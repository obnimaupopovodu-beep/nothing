# Кабинеты uwbelieve

Актуальная инструкция по запуску, двум поддоменам и командам: [launch-accounts.md](launch-accounts.md).

## Что готово локально

Один Next.js проект обслуживает лендинг, кабинет артиста и рабочую область команды.
Все реальные данные используют **тот же существующий проект Supabase**, что и
`demo_submissions`. Дополнительная база или отдельный проект Supabase не нужны.

- `/login`: вход, регистрация артиста, подтверждение email и восстановление пароля.
- `/artists`: обзор; `/artists/releases`: каталог релизов.
- `/artists/releases/new`: форма из пяти шагов.
- `/artists/releases/:id`: редактирование доступного черновика или просмотр статуса и обратной связи.
- `/artists/profile`: имя артиста, legal names, Spotify / Apple Music IDs.
- `/artists/notifications`: уведомления о смене статуса и замечаниях.
- `/admin`: обзор команды; `/admin/releases`: очередь проверки.
- `/admin/releases/:id`: metadata, credits, история, решения и комментарий артисту.
- `/admin/artists`: профили; `/admin/demos`: существующий демо-инбокс.
- `/admin/login`: переход на общий вход в рабочую область команды.

**Схема удалённой базы этим изменением не изменялась.** До выполнения SQL реальные
кабинеты не смогут загружать или сохранять данные. Действующая авторизация администратора
через общий пароль заменена Supabase Auth: для нового `/admin` понадобится аккаунт с ролью команды.

## Как посмотреть без базы

```bash
npm run dev
```

Откройте:

- http://localhost:3000/preview — кабинет артиста с явно обозначенными примерными данными.
- http://localhost:3000/preview?workspace=admin — рабочая область команды.
- http://localhost:3000/preview?view=new — все шаги формы релиза.
- http://localhost:3000/login — реальная страница входа.

Предпросмотр доступен только при `npm run dev`. Он не выдаёт сессию и не обходит
авторизацию API. Сохранение, отправка и загрузка файлов в предпросмотре отключены.
Изменения полей исчезают при перезагрузке.

## Подключение позже через SQL Editor

### 1. Выполнить основную схему

В **существующем** проекте Supabase → SQL Editor создайте новый запрос и вставьте
**весь файл**:

`supabase/migrations/20261002103108_artist_platform.sql`, затем
`supabase/migrations/20261002213408_artist_team_access.sql`.

Нажмите Run **один раз**. Файл создаёт таблицы `label_*`, служебную схему
`label_private`, функции для атомарного сохранения и переходов, RLS и приватный
bucket `label-artwork`. Существующие записи `demo_submissions` остаются на месте.

Этот файл предполагает проверенную текущую структуру `demo_submissions`:
`id uuid`, `alias`, `email`, `sc_link`, `notes`, `status`, `created_at`.
Правила демо-инбокса меняются: анонимный посетитель может только добавить новую
заявку; читать, менять статус и удалять заявки может только команда. Изменение
контактных данных через клиентский API запрещено.

Это одноразовая миграция: повторный запуск целиком завершится ошибкой существующих
объектов. Если SQL Editor сообщил ошибку, не продолжайте отдельными кусками;
передайте полный текст ошибки для исправления. Не добавляйте `label_private`
в список схем, доступных Data API.

### 2. Переменные окружения

Сверьте `.env` / `.env.local` с `.env.example`. Поддерживаются и прежние
`SUPABASE_ANON_KEY` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

- `SUPABASE_URL`: URL этого существующего проекта.
- `SUPABASE_PUBLISHABLE_KEY`: его publishable key.
- `SUPABASE_SERVICE_ROLE_KEY`: server-only ключ того же проекта; нужен для обложек.
- `SITE_URL`: абсолютный адрес приложения (`http://localhost:3000` локально).

Service role не используется для чтения или редактирования релизов пользователями;
такие запросы выполняются с проверенной пользовательской сессией и RLS.
Не добавляйте secret/service role в переменные `NEXT_PUBLIC_*`.
После изменения env перезапустите dev-сервер. На хостинге задайте production значения
и правильный `SITE_URL`; не переносите локальный адрес из `.env.local` в deployment.

### 3. Настроить Supabase Auth

В Authentication → URL Configuration:

- Site URL: адрес приложения.
- Redirect URLs: `http://localhost:3000/auth/callback` для локальной разработки,
  и `/auth/callback` на каждом используемом production домене.

Включите Email provider и подтверждение email; для доставки реальных писем настройте
SMTP. Используется PKCE: ссылку из письма нужно открыть в том браузере и на том домене,
где началась регистрация / восстановление. Ошибки ссылки возвращают на страницу входа.
Supabase Auth отвечает за ограничения частоты входа, регистрации и восстановления.
Страница восстановления доступна после ссылки из письма; новая парольная сессия
проверяется Supabase, другие активные сессии отзываются.

### 4. Первый аккаунт команды

Зарегистрируйте аккаунт через `/login`, подтвердите email и выполните первый вход:
это создаст профиль и базовую роль `artist`.

Затем **самостоятельно** в SQL Editor выполните этот запрос с нужным email:

```sql
insert into public.label_roles (user_id, role)
select id, 'admin'
from auth.users
where lower(email) = lower('YOUR_TEAM_EMAIL@example.com')
on conflict do nothing;
```

Для менеджера замените `admin` на `label_manager`. Эти роли дают доступ к поданным
релизам, профилям и демо-инбоксу. Обычный пользователь не может выдать себе роль
через форму, REST API или `user_metadata`. Один аккаунт может использовать оба кабинета.
Роль проверяется по базе при каждом запросе, без ожидания обновления JWT.

Проверьте назначение:

```sql
select u.email, r.role
from public.label_roles r
join auth.users u on u.id = r.user_id
where lower(u.email) = lower('YOUR_TEAM_EMAIL@example.com');
```

## Поддомены

Привяжите `artists.uwbelieve.com` и `label.uwbelieve.com` к тому же Next.js deployment,
затем задайте `ARTIST_HOSTNAME` и `ADMIN_HOSTNAME` (только hostname).
Middleware направляет корень и короткие workspace пути в соответствующий кабинет.
Полные пути `/artists/...` и `/admin/...` тоже работают. Сам hostname не выдаёт права:
API, серверные страницы и RLS продолжают проверять аккаунт и роль.

Cookies host-only, HttpOnly, SameSite=Lax и Secure в production. Вход на разных
поддоменах выполняется отдельно; пользователи и права находятся в одной системе Auth.
Поддомены можно добавить позже: сейчас достаточно путей на основном домене.

## Жизненный цикл и правила

```text
Draft → Submitted → In review → Approved → Delivered
                         ↓
                 Changes requested → Submitted
```

- Артист редактирует только свои `draft` / `changes_requested` релизы.
- Команда видит поданные релизы; чужие неотправленные черновики скрыты.
- Перед отправкой нужны title, genre, будущая дата, хотя бы один primary artist,
  названия и язык треков, composer на каждом треке и полные legal names в credits.
- Single содержит один трек; EP / album поддерживают до 40 треков.
- Профиль не является заменой credits: имена подставляются при создании, затем
  сохраняются отдельно в релизе. Artwork необязателен.
- Запрос правок требует комментарий. Комментарий виден артисту в истории.
- Дата остаётся пожеланием артиста; этот MVP не интегрирован с дистрибьютором.
  `Delivered` — ручная отметка команды после фактической доставки.
- При параллельном редактировании `revision` защищает от перезаписи чужих изменений.
- Поля черновика не сохраняются автоматически: используйте Save draft.
- Один релиз принадлежит одному аккаунту артиста; редакторы его команды могут
  работать с существующими черновиками, наблюдатели — читать. Новые релизы
  создаёт владелец. Featured artists — metadata.
- Каталог показывает последние 200 релизов; история — последние 50 событий,
  уведомления — последние 100. Для дальнейшего роста нужна пагинация.

## Artwork

Подписанная ссылка даёт временное право загрузить один файл напрямую в Supabase
Storage. Это обходит ограничения размера тела запроса серверного хостинга.
Публичный доступ к bucket отключён; привязать файл к релизу может только backend.

После загрузки backend скачивает объект и через Sharp проверяет настоящий формат,
RGB, квадрат 3000–6000 px, отсутствие анимации, ограничение 20 MB и полный decode.
Сохраняется SHA-256. Расширение и MIME браузера не считаются доказательством формата.
Поданные релизы блокируют замену artwork; файл имеет уникальный путь и не перезаписывается.
Просмотр использует короткую подписанную ссылку на 5 минут.

На одного пользователя ограничены ожидающие загрузки. Брошенные загрузки и старые
заменённые обложки не очищаются автоматически в MVP: перед ростом трафика добавьте
плановое удаление непривязанных файлов с учётом срока подписанных ссылок.

## Проверка локально

```bash
npm run test:platform
npx tsc --noEmit
npm run build
```

`test:platform` поднимает изолированный PostgreSQL через PGlite с тестовыми заменами
`auth.uid()`, `auth.jwt()` и Storage metadata, выполняет **тот же SQL-файл** и проверяет
42 сценария доступа и workflow: анонимный доступ, IDOR, повышение роли, права на
вложенные credits, запрет редактирования после отправки, конфликты revisions,
запрос правок, подтверждение и доставка, уведомления и приватность artwork.

Тест не подключается к Supabase и не создаёт там аккаунты. После ручного SQL setup
нужна проверка на реальных Auth сессиях: два артиста, аккаунт команды, чужие ID,
email callback и валидная / некорректная обложка. Supabase Security Advisors проверьте
после применения SQL; локальный PostgreSQL не проверяет настройки проекта Auth / SMTP.

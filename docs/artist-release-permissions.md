# Прямые релизы для отдельных артистов

## Установка

1. До обновления приложения выполните целиком файл
   `supabase/migrations/20261101142353_artist_direct_release_permissions.sql`
   в SQL Editor существующего проекта Supabase. Требуются все четыре предыдущие
   миграции кабинетов, включая `20261004174646_unified_demo_and_manual_releases.sql`.
   Скрипт выполняется одной транзакцией; повторно запускать его не нужно.
2. После успешного применения SQL разверните обновлённое приложение.
   Новые переменные окружения не нужны. Схему `label_private` не открывайте для Data API.

Рабочая база и развёртывание при локальной разработке не менялись.

## Настройки артиста

В кабинете лейбла откройте **Artists → шестерёнка у артиста**. Admin и Label manager
могут выбрать один режим и сохранить его:

- **Demo approval required** — для нового релиза требуется одобренное демо.
- **Allow one release without a demo** — разрешён один новый релиз напрямую.
  Разрешение расходуется при первом успешном сохранении черновика, в том числе
  при автоматическом сохранении перед загрузкой обложки. Ошибка сохранения
  не расходует разрешение. Повторный выбор этого режима выдаёт новый разовый допуск.
- **Allow releases without demos** — новые релизы можно создавать напрямую,
  пока лейбл не изменит этот режим.

Артист должен подтвердить email, прежде чем ему можно выдать прямой доступ.
Сохранение режима `Demo approval required` отзывает допуск для новых релизов.
Уже созданные черновики можно продолжать редактировать и отправлять, в том числе
после запроса исправлений. Создание релиза по одобренному демо не расходует разовый
допуск. Создание релизов самим лейблом также работает независимо от допуска артиста.

## Кабинет артиста

При наличии допуска на главной кабинета и в **My releases** появляется **New release**.
Артист сразу заполняет существующую форму метаданных, треков и обложки.
Обычная проверка лейблом, статусы и требования к релизу продолжают действовать.
Допуск не означает автоматическое одобрение или доставку релиза.

Права выдаются конкретному аккаунту. Участник команды не может использовать чужой
допуск для создания нового релиза, но сохраняет предусмотренные командной ролью
права редактирования уже созданных релизов.

## Защита и проверка

Разрешения хранятся в таблице с RLS. Артист видит только собственный режим,
а запись разрешена только через RPC с проверкой роли лейбла. Одноразовый допуск
проверяется и расходуется в той же транзакции, что создаёт релиз; строка разрешений
блокируется на время сохранения. Два запроса не могут создать два релиза по одному
допуску. Подделка `owner_id` или `demo_submission_id` не обходит эти проверки.

- `npm run test:platform` — изолированные проверки PostgreSQL/RLS и сценариев релизов.
- `npm run typecheck` — TypeScript.
- `npm run lint` — ESLint.
- `npm run build` — production-сборка.
- При `npm run dev` откройте `/preview?workspace=admin&view=artists`, чтобы
  проверить окно настроек на примерах без входа и без изменений реальных аккаунтов.
